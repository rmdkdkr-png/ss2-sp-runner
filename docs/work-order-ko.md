## 0. 이 프로젝트가 무엇인가

> 게임 자체의 입력 결함과 플레이어인 저의 손 결함에 대해
> **모던 모드**를 만들어보고자 하였던 몸부림입니다.

네오지오 포켓 컬러용 『사무라이 스피리츠! 2』(한글 패치본)를 브라우저에서 돌리면서,
**필살기 커맨드를 버튼 하나로 대체**하는 모바일 조작 레이어를 얹은 도구다.
산출물은 **HTML 파일 한 장**이며 롬은 포함하지 않는다.

핵심 동작은 세 가지다.

1. **커맨드 대행** — SP 버튼을 누르면 실행기가 `↓↘→ + A` 같은 원본 커맨드를
   프레임 단위로 에뮬레이터 패드에 밀어 넣는다.
2. **방향 자동 미러링** — 캐릭터가 보는 방향을 게임 RAM에서 읽어 커맨드 좌우를 자동으로 뒤집는다.
   사용자에게 좌우 전환 스위치를 노출하지 않는다.
3. **입력 히스토리 리셋** — 게임의 커맨드 매처가 이전 입력 잔재 때문에 오작동하는 문제를
   RAM 플래그 한 바이트로 해소한다(§2-3).

## 2. 검증된 사실 (재확인 불필요)

### 2-1. RAM 맵

주소는 **SYSTEM_RAM 오프셋**이다. TLCS-900/H CPU 주소 = `0x4000 + 오프셋`.

| 이름 | 오프셋 | 내용 |
|---|---|---|
| ACT | `0x0E3E` | P1 액션 ID (u16LE). `≥0x180` = 필살기 계열 |
| P1 Y | `0x0E3A` | 지상 = 128 (전 스테이지 불변), 공중 = 66~99 |
| P1 X / P2 X | `0x0E38` / `0x0E78` | 거리 계산용 |
| FACING | `0x0E54` | 1 = 왼쪽을 봄 |
| CHARSTYLE | `0x1B51` | `>>3` = 블록 = `2×캐릭터인덱스 + 유파` |
| CARD 슬롯 | `0x1B56`, `0x1B57` | 로컬 idx 0~3, `0xFF` = 빈칸 |
| P2 HP | `0x1C46` | max 128. 히트 컨펌은 HP 감소로 판정(가드 = 노데미지) |
| HITSTOP | `0x1DC7` | 타격 성립 시 5 → 2프레임당 1 감소, 평시 0 |
| **CMDRESET** | **`0x1DCD`** | **1을 쓰면 게임이 자기 입력 링 커서를 초기화한다** |
| 입력 링 | `0x1DD1`~`0x1E50` | 0x80바이트. 원시 패드 비트 기록 |
| MODE | `0x00A7` | 메뉴/전투 구분 |

패드 레지스터: SYSTEM_RAM `0x2F82` (CPU `0x6F82`).
비트 — `UP=01 DOWN=02 LEFT=04 RIGHT=08 A=10 B=20`. 대각은 OR.

### 2-2. 지원 ROM (SHA-256 앞 6바이트)

| ROM | romKey |
|---|---|
| v0.70 allcards | `fc1427882131` |
| v0.89 일반판 | `c423fd0cbd62` |
| v0.89 allcards | `f698c5287995` |

**RAM 오프셋은 세 버전에서 동일**하고, v0.70에서 만든 세이브스테이트가 v0.89에서 그대로 로드된다.

### 2-3. 커맨드 매처의 성질 — 이 프로젝트의 근본 문제

게임의 커맨드 매처(ROM `0x202E8B`)는 입력 링을 **역방향으로 스캔하면서 불일치 샘플을 건너뛴다.**
즉 부분수열 탐색이라, 이전에 남아 있던 입력이 새 커맨드와 섞여 **엉뚱한 기술을 가로챈다**.

**해법:** 커맨드를 밀어 넣기 직전에 `0x1DCD = 1`을 쓴다. 다음 샘플부터 게임 자신의 리셋 경로가
돌아 커서·센티널 일관성이 보존된다.

| 케이스(하이재킹 7종 × 6회) | 무보정 | `0x1DCD=1` |
|---|---|---|
| 합계 | 0/42 | **41/42** |

과거에 쓰던 "약베기 플러시" 방식은 3연참을 **0/3으로 파괴**했고, 리셋 방식은 **3/3 무손상**이다.
추가 지연 0프레임.

> 상세 디스어셈블·재현 절차는 별첨 **`외주브리프_SS2_커맨드엔진_리버스.md`** 참조.

## 3. 아키텍처

```
사무라이스피리츠2_SP실행기.html   (단일 파일, ~132KB)
├─ 랜딩 : 롬 드래그&드롭 → IndexedDB 보관 → romKey(SHA-256 앞 6B)로 식별
├─ EmulatorJS 4.2.3 (CDN 고정)  ─ 코어 ngp = beetle-ngp / mednafen
├─ 조작 레이어 : 절대배치 DOM 버튼 + 포인터 이벤트
└─ 매크로 엔진
     ├─ 프레임 소스 : gameManager.getFrameNum()  ← rAF 아님. 에뮬 프레임에 잠금
     ├─ 컴파일      : 기술 → [{방향, 버튼, 유지프레임}] 스텝 배열
     ├─ 전처리      : FACING 읽어 좌우 미러 + CMDRESET 쓰기
     └─ 게이트      : HITSTOP / 공중(Y) / 카드 장착 여부 확인
```

**설계 원칙 — 지켜야 할 것**

* 매크로는 **에뮬레이터 프레임**에 동기화한다. `requestAnimationFrame`이나 `setTimeout` 기반으로
  되돌리지 말 것. (rAF는 터치 중 브라우저 스케줄러에 굶어 죽는다 — 실측)
* 조작부 CSS는 **재합성 비용이 0에 수렴**하도록 유지한다. 새 시각 효과를 넣기 전에
  CPU 4× 스로틀 연타 실측을 먼저 하라.
* RAM 읽기는 프레임당 최소로. 과거에 프리징을 일으켰다.

## 4. 발주 항목

우선순위 순. 각 항목에 **범위 / 완료 기준 / 참고**를 명시했다.

### A. 코어 내장판의 체감 속도 — **최우선**

**배경.** 매크로를 JS가 아니라 libretro 코어(`ss2sp.c`) 안에서 돌리는 판을 만들어
네이티브·브라우저 양쪽에서 동작을 확인했다(중립 발동 4/4, 네이티브 12/12·15/15).
그런데 **실기 체감이 순정 NGP 에뮬레이터보다 눈에 띄게 느리다.**

지금까지 확인한 것:

* 코어 옵션(`ngp_ss2sp`) 자체의 비용은 **−0.4%, 즉 없음**. 엔진은 범인이 아니다.
* RetroArch 렌더 스택을 최대한 걷어내 wasm 3.54MB → **2.25MB (−37%)**.
  로드·메모리는 개선됐지만 **프레임당 CPU는 그대로**다.
* 4개 코어 파일명이 전부 legacy 빌드로 매핑돼 WebGL2 기기가 GLES2로 강등되던 버그는 수정했다.
* 비교 대상(순정 NGP 에뮬레이터)은 **RGB565**로 그린다.

**의뢰 범위**

1. RetroArch emscripten 빌드에서 프레임당 비용의 실제 분포를 프로파일링(코어 실행 / 비디오 변환 / GL 제출).
2. ~~픽셀 포맷을 XRGB8888 → RGB565로~~ — **닫힘.** GL 후킹으로 확인한 결과
   매 프레임 업로드가 이미 `format=RGB, type=UNSIGNED_SHORT_5_6_5`다
   (`Makefile`의 `FRONTEND_SUPPORTS_RGB565=1`). 변환 단계가 없다.
3. `video_driver` 경로에서 제거 가능한 단계(스케일러, 필터 체인, 위젯)를 식별.
4. 개선이 구조적으로 불가능하다면 **그 근거를 문서로** 남기고 종료해도 좋다.

**완료 기준** — 동일 기기·동일 롬에서 순정 대비 프레임 타임 격차를 수치로 제시하고,
줄일 수 있는 항목과 그 이득을 각각 실측치로 제시할 것.
**절차·금지사항·합격 기준은 `검수지시서_SS2_저속끊김_외주용.md`를 따른다.**

**참고** — `코어이식_타당성보고서_RetroArch.md`, `SS2_코어이식_프로토타입.zip`,
`core-sp/wasm/BUILD_NOTES.md`(emscripten 3.1.6 강행 시 우회 9건).

### B. 관대매칭 규칙의 형식화

**배경.** 매처가 부분수열 탐색이라 짧은 커맨드가 긴 커맨드를 가로챈다.
`0x1DCD` 리셋으로 대부분 해소됐지만, **어떤 커맨드 쌍이 서로를 가로채는지**를
사전에 알 수 있으면 SP 자리 자동 배치를 훨씬 똑똑하게 만들 수 있다.

**의뢰 범위** — ROM `0x202E8B` 매처를 형식적으로 기술하고
(토큰 테이블 형식 `[탐색 예산][역순 토큰…][FF]` 기준), 전 캐릭터·전 유파의
커맨드 테이블을 덤프해 **충돌 행렬**을 산출.

**완료 기준** — `charIdx × style × move` → 커맨드 토큰열 JSON, 그리고
"A를 의도했을 때 B가 나올 수 있다"의 방향성 있는 충돌 목록.

### C. 미검증 데이터 정리

* **우쿄 나찰 무소 카스미 `214`** — 리셋 적용 후에도 5/6. 나머지 1회의 실패 위상 규명.
* **스크립트 포인터 `0x1A15`** 의 정체.
* 히트박스/판정 테이블(§B 부록 참조) — 콤보 마무리 자동 선택 정확도를 올리는 데 쓰인다.

## 5. 변경 금지 제약 (발주자 확정 사항)

이 항목들은 기술적 판단이 아니라 **제품 결정**이다. 임의로 뒤집지 말 것.

1. **롬을 산출물에 포함하지 않는다.** 어떤 형태로도.
2. **좌우 전환 토글을 노출하지 않는다.** 방향은 자동 감지, 커맨드는 자동 미러링.
3. **롬 한 종류만 지원한다.** 다른 게임·다른 패치본으로 일반화하지 않는다.
4. **헛잡기(불발 잡기)도 발동해야 한다.** 게이트에서 걸러 내지 말 것.
5. **카드 전용 버튼과 전용 초필살기 버튼을 따로 두지 않는다.** 일반 기술 목록에 통합한다.
6. **화면 필터 기능은 유지한다.** 성능상 불리해도 발주자가 켜서 쓴다. 기본값만 조정 가능.
7. 배포판은 **코어를 내장하지 않는다.** 단일 HTML + CDN 구성을 유지한다.

## 6. 검증 방법

### 브라우저 회귀 (필수)

```bash
cd ejs && python3 regress.py      # Playwright 헤드리스, 36 checks
```

12개 그룹으로 나뉜다 — 부팅/롬 인식, 레이아웃·설정, 캐릭터 감지, 매크로 컴파일,
방향 미러링, 프레임 보정 부재 확인, 커맨드 리셋, 콤보, 세이브·로드(매크로 중단 포함),
빨리감기, 드래그 편집, 페이지 에러 0.

**36/36이 아니면 머지 금지.**

### 네이티브 하네스 (리버스용)

`mednafen_ngp_libretro_ss2sp.so` + 파이썬 하네스로 프레임 단위 제어·RAM 덤프가 가능하다.
브라우저보다 100배 빠르게 시행 횟수를 벌 수 있으므로,
**커맨드 성공률 같은 통계는 반드시 여기서** 낸다.

> ⚠️ 브라우저에서 성공률을 재면 COM이 때려 히트스톱이 걸리고 매크로가 끊긴다.
> 이 함정을 이미 두 번 밟았다. 네이티브에서는 COM을 중화하고 잰다.

## 8. 협업 시 알아 두면 시간을 아끼는 것

* **`make`가 헤더 의존성을 추적하지 않는다.** `ss2sp_moves.h`를 재생성했으면
  `ss2sp.o`를 직접 지워야 한다. 안 지우고 하루를 날린 적이 있다.
* **캐릭터 인덱스는 표시 순서가 아니다.** 내부 인덱스(`0x1B51>>3`)를 쓴다.
* **libretro.c의 extern 선언은 파일 상단에.** emscripten은
  `-Werror=implicit-function-declaration`이라 아래쪽에 두면 빌드가 깨진다(gcc는 경고만 낸다).
* **EmulatorJS의 코어 IndexedDB 캐시**(`EmulatorJS-core`)가 이전 코어를 계속 먹인다.
  커스텀 코어를 시험할 때 이것 때문에 "SP만 안 되는" 현상을 겪었다.
  `?debug=1`은 캐시를 건너뛰므로 테스트가 통과해 버려 원인 파악이 늦어진다.
* **상태 로드 후 매크로 잔재**는 브라우저·코어 양쪽에서 각각 물렸다.
  로드/리셋 경로에서 반드시 매크로를 중단시켜야 한다.
* **측정하지 않은 최적화는 넣지 않는다.** devicePixelRatio 캡을 걸려다
  캔버스가 이미 1:1임을 확인하고 되돌린 적이 있다. 만들기 전에 재라.
