# SS2 SP 실행기 — 저속·끊김 문제 검수 / 수정 지시서

**대상:** `사무라이스피리츠2_SP실행기.html` (v0.7)
**개정:** 2차 검수 반영 — §2의 전제가 계측으로 뒤집혔고, **원인 하나를 찾아 고쳤다.** §0을 먼저 읽을 것.
**목표:** 기능을 추가하지 말고, 현재 기능을 유지하면서 모바일에서 느려지는 원인을 찾아 제거한다.
**동봉:** `perf_ab.py` (계측 하네스 — 아래 모든 항목을 자동 실행한다)

> 현재 코드에는 과거 프레임 저하 원인으로 확인되어 **이미 제거된** 부분이 상당수 있다.
> 감으로 DOM/CSS를 뜯지 말고 **계측 → A/B → 수정** 순서로 진행할 것.

## 0. 2차 검수에서 결론난 것 — 여기부터 읽을 것

### ★ 터치 중 끊김의 원인을 찾았다: **캔버스가 반투명이었다**

EmulatorJS는 WebGL 컨텍스트를 `alpha:true` · `premultipliedAlpha:true`로 만든다.
그러면 브라우저 합성기가 **매 합성마다 캔버스를 페이지 배경과 블렌딩**한다.
터치 중에는 합성기가 이미 바쁘므로, 이 블렌딩 한 겹이 에뮬레이터 루프를 굶긴다.

`getContext`를 감싸 `alpha:false, premultipliedAlpha:false`로 강제한 결과
(412×915, 디패드 드래그 8초 × 2회):

| | emu FPS | 끊김(>33ms) |
|---|---|---|
| 기본 (`alpha:true`) | 51.8 / 51.9 | 65 / 64 |
| **`alpha:false`** | **59.6 / 59.6** | **3 / 2** |

**v0.7에 반영 완료.** 회귀 10.8이 캔버스 불투명을 검사한다.
게임 화면은 어차피 불투명하므로 잃는 것이 없다.

### ★ RGB565 항목은 **닫혔다** — 이미 RGB565로 돌고 있다

발주서가 최우선으로 걸었던 "XRGB8888 → RGB565"는 **전제가 틀렸다.**

1. `beetle-ngp-libretro/Makefile` 최상단에 `FRONTEND_SUPPORTS_RGB565 = 1`
   (emscripten 플랫폼 블록에서 덮어쓰지 않는다) → 코어는 `RETRO_PIXEL_FORMAT_RGB565`로
   `SET_PIXEL_FORMAT`을 부르고 `RETRO_PIX_DEPTH = 16`이 된다.
2. 실행 중 WebGL 호출을 후킹해 확인한 **매 프레임 업로드 경로**:

```
   7384회  texSubImage2D  format=RGB  type=UNSIGNED_SHORT_5_6_5
```

**변환 없이 565 그대로 GPU에 올린다.** 8888로 부풀리는 단계가 프레임 경로에 없다.
사용자가 관찰한 "순정 NGP 에뮬은 RGB565로 한다"는 우리 쪽도 이미 같다.

→ 이 항목에 시간을 쓰지 말 것. 코어를 다시 빌드할 이유가 없다.

### ★ `applyDir()`의 4× `simulateInput()` — 비용 없음, **고치지 말 것**

지적대로 방향 한 번에 U/D/L/R 4회를 보내고, 그중 77~88%가 같은 값의 재전송이다.
그런데 실제 비용을 재 보면:

| | 호출 수 | 누적 시간 | 벽시계 대비 |
|---|---|---|---|
| SP 연타 10초 | 208회 | 0.1ms | **0.001%** |
| 콤보 연타 10초 | 304회 | 0.3ms | **0.004%** |
| SP 연타 10초 (CPU ×4 스로틀) | 128회 | 1.0ms | **0.01%** |

**측정 가능한 비용이 아니다.** 지적하신 대로 "게임이 매 샘플을 필요로 하면 입력 판정이
깨질 수 있는" 위험이 있는데, 그 위험을 감수해서 얻을 이득이 0이다. **현행 유지.**

## 1. 절대 건드리지 말 것

### ① 자동 frameskip / vsync

자동 frameskip은 **이미 제거되어 있다.** 과거 실측:

| | 유휴 | 연타 |
|---|---|---|
| vsync 유지 | 56.6 fps | **59.1 fps** |
| vsync OFF | 60.2 fps | **44.7 fps** |

vsync를 끄거나 별도의 자동 frameskip을 다시 넣지 말 것. **역효과가 실측으로 확인되어 있다.**

### ② `getState()` 상시 polling

현재 RAM 접근은 대부분 `HEAPU8` 직접 읽기다. `getState()`를 프레임마다 부르는 방식으로 되돌리지 말 것.
(`getState()`는 프레임 정지를 유발해 전투 중 호출을 막아 놓았다.)

### ③ 600ms 통합 polling

컨텍스트 / 캐릭터 자동감지 / HUD가 **하나의 600ms 타이머**에 통합되어 있다.
쪼개거나 고빈도로 바꾸지 말 것.

### ④ 입력 판정 로직

D-pad는 `getBoundingClientRect()`를 매 `pointermove`마다 부르지 않고 캐시한다.
과거 강제 reflow 문제를 해결한 부분이다.

## 3. Shader는 반드시 별도 A/B

기본값은 OFF다. **OFF → CRT/zfast → 2x → 4x** 순서로 비교한다.

* **OFF에서도 느리다** → shader는 범인이 아니다. §2의 픽셀 포맷으로 간다.
* **ON에서만 급락한다** → shader 경로를 최적화하거나 기본값을 OFF로 유지한다.

shader는 EmulatorJS `enableShader()`로 직접 적용된다.

## 4. 코드에서 발견된 실제 잔여 부하 — **v0.6~0.7에서 처리함**

### ① `.armed`의 `box-shadow` — 제거 완료

A/SP 강 판정 시 `box-shadow: 0 0 18px`가 남아 있었다.
하필 **버튼을 누르고 있는 동안** 켜져서 blur/compositing 비용을 계속 만들었다.
→ `background` + `border-color` 변경으로 대체. **조작부에 box-shadow는 이제 0건이다**
(회귀 10.6이 이를 검사한다).

### ② SP 버튼 라벨 — 제거 완료 (신규 발견)

`refreshSpLabel()`이 `setDirs()`에서 불렸다. 즉 **디패드를 한 칸 움직일 때마다**
`readGame()`(힙 읽기) + `curSpMap()`(객체 생성) + DOM 텍스트 쓰기가 돌았다.
600ms 폴링에서만 도는 줄 알았던 코드다.
→ 라벨 자체를 없앴다. 정보는 [기술] 팔레트와 [캐릭터] 시트에 이미 있다.

### ③ 캔버스 반투명 — 제거 완료 (v0.7, §0 참조)

**이것이 터치 중 끊김의 실제 원인이었다.** `getContext`를 감싸 불투명으로 강제한다.

### ④ 전역 `addEventListener` 패치 — 한시적으로 변경 (지적 반영)

`EventTarget.prototype.addEventListener`를 감싸 window/document의 포인터·터치 리스너를
passive로 강등하고 있었다. 영구 패치면 **나중에 붙이는 리스너까지 조용히 passive**가 되어
`preventDefault`가 먹지 않는다.
→ 노리는 대상(EJS 로더·nipplejs)은 초기화 때 등록을 끝내므로 **부팅 2초 후 원본으로 복원**한다.
회귀 10.9가 복원을 검사하고, 11.1·11.2가 배치 편집 모드를 검사한다.

## 5. SP 연타 시 별도 검수 — **§0에서 종결됨. 실기 재현만 남았다**

매크로는 에뮬레이터의 **실제 frame counter**로 진행한다. 다음을 따로 측정한다.

| | 시나리오 | 기대 |
|---|---|---|
| A | 아무것도 안 누름 | 60fps |
| B | D-pad 연속 입력 | 저하 없음 |
| C | A 연타 | 저하 없음 |
| D | SP 연타 | 저하 없음 |
| E | SP + D-pad 동시 연타 | 저하 없음 |
| F | 콤보 연속 사용 | 저하 없음 |

**E/F에서만 떨어진다면** 렌더러보다 **JS→WASM 입력 호출**을 의심한다.
방향 입력은 상태가 실제로 변했을 때만 `applyDir()`을 부르도록 최적화돼 있지만,
매크로는 한 스텝마다 U/D/L/R + 버튼을 각각 `simulateInput()`으로 넘긴다.
이 구간을 profiler로 확인하고, **호출 횟수를 줄이는 방향**으로 볼 것.

## 6. `watchFire()` A/B — **노이즈 수준으로 확인됨 (§10)**

발동 결과 확인은 기본 ON이고 최대 약 1.2초 동안 100ms 간격으로 RAM을 읽는다.

**WATCH ON vs OFF**를 SP 연타 중에 비교한다.

* 차이 없음 → 유지.
* 차이 있음 → 100ms 폴링을 **발동 가능성이 높은 짧은 구간에서 최소 횟수**로 줄인다.

## 7. 첫 입력만 느린 경우

> ⚠️ `perf_ab.py`의 이 항목은 **전투 화면에서 돌려야 한다.** 타이틀/데모에서는
> ACT가 필살기 값으로 바뀌지 않아 측정이 `None`으로 나온다(1차 판본은 힙 탐색 시간만 재고
> "첫 SP"라고 이름 붙였던 오류가 있었다 — 지적 반영해 실제 발동 지연을 재도록 고쳤다).


커맨드 버퍼 리셋을 위해 초기 힙 탐색(경우에 따라 `getState()`)이 발생할 수 있다.

「게임 시작 → 첫 SP」와 「게임 시작 10초 후 → SP」를 비교한다.
**첫 입력만 느리면 초기화·힙 탐색 문제**이며,
해결책은 **게임 시작 시 1회 미리 확보**하는 것이지 전투 중 polling을 늘리는 것이 아니다.

**게임 자체의 60fps를 희생해 UI가 빨라 보이게 만드는 수정은 불인정.**

## 10. 발주자 측 사전 계측 (참고용 · 실기 아님)

**SwiftShader(소프트웨어 GL)** 환경이므로 **절대값은 기기 수치가 아니다.**
순위와 경향만 참고하고, 합격 판정은 반드시 실기에서 같은 스크립트로 낼 것.

측정 조건: 412×915, 조건당 8초, CPU 스로틀 없음.

| 필터 | emu FPS | p95 | max | 끊김(>33ms) |

| **게임 캔버스 드래그 (앱 핸들러 없음)** | **43.5 / 44.0** | 123 / 118 |

**핸들러가 없는 쪽이 더 느리다.**
즉 터치 중의 프레임 저하는 **앱의 D-pad·버튼 코드가 만드는 것이 아니라,
브라우저가 포인터 이벤트를 처리하면서 에뮬레이터 루프를 굶기는 데서 온다.**
→ §9의 "여기부터 건드리는 건 시간 낭비"를 수치가 뒷받침한다.
→ 사용자 제보 "B도 디패드도 허공도 (다 끊긴다)"와도 일치한다.

### watch A/B (§6)

| | emu FPS | 끊김 |
|---|---|---|
| watch ON | 55.4 | 36 |
| watch OFF | 53.1 | 55 |

**OFF가 더 나쁘게 나왔다 = 노이즈 범위.** 이 환경에서 `watchFire()`는 비용이 아니다.
실기에서 재확인은 하되, 우선순위는 낮다.

### 힙 탐색 (§7)

최초 **0.4ms** / 재탐색 0.1ms. 한 프레임(16.7ms)에 한참 못 미친다.
**"첫 입력만 느림"은 힙 탐색 때문이 아니다.**

## 11. 계측 하네스 사용법

```bash
# 실행기를 서빙한 뒤
python3 perf_ab.py                      # 전부
python3 perf_ab.py shader               # 필터 A/B만
python3 perf_ab.py input                # 입력 시나리오만
SECS=30 python3 perf_ab.py              # 제출용은 30초 이상
THROTTLE=4 python3 perf_ab.py input     # 저사양 CPU 흉내
URL=... ROM=... python3 perf_ab.py      # 다른 빌드/롬으로
```

출력 항목:

| | 뜻 |
|---|---|
| `emu_fps` | `getFrameNum()` 증가량 / 초 — **에뮬레이터가 실제로 돈 프레임** |
| `disp_fps` | rAF 호출 수 / 초 — 표시 프레임 |
| `p95` / `max` | rAF 간격(ms)의 95퍼센타일 / 최대 |
| `long` | 33ms(2프레임) 넘긴 간격 횟수 = 체감 끊김 |

**`emu_fps`와 `disp_fps`를 반드시 나눠서 보고할 것.**
둘이 같이 떨어지면 렌더 경로, `disp_fps`만 떨어지면 표시 경로다.

## 12. 최종 합격 기준

### 정상

* 일반 플레이: 60fps 근접 유지
* D-pad 조작: 프레임 저하 없음
* SP 연타: 프레임 저하 없음
* 콤보: 프레임 저하 없음
* 화면 필터 OFF: 안정적인 60fps
* 첫 입력 이후 지속적인 끊김 없음

### 불합격

* 터치할 때마다 순간적으로 프레임 급락
* SP 연타 후 한동안 계속 끊김
* 콤보 사용 후 프레임 회복 지연
* 60 → 40fps대 반복
* **vsync OFF로만 빨라짐**
* **frameskip으로만 빨라짐**
* **입력을 늦춰서 문제를 감춤**

## 13. 발주자 판정 — 의심 순위

| 항목 | 1차 의심도 | 2차 계측 후 |
|---|---|---|
| **캔버스 합성 블렌딩 (`alpha:true`)** | (후보에 없었음) | ✅ **원인 확정 · v0.7에서 수정** |
| XRGB8888 → RGB565 | ★★★★★ | ❌ **이미 565다 — 닫힘** |
| Shader | ★★★★☆ | 🟡 4x만 남음 (기본 OFF) |
| SP 매크로 JS→WASM 호출 | ★★★☆☆ | ❌ 0.01% 미만 — 닫힘 |
| 발동 확인 RAM polling | ★★☆☆☆ | ❌ 노이즈 — 닫힘 |
| 600ms polling | ★☆☆☆☆ | ❌ 닫힘 |
| 일반 DOM / CSS | ★☆☆☆☆ | ❌ 대조군에서 반증 — 닫힘 |
| frameskip 제거 / vsync | 건드리면 안 됨 | 그대로 |

"코어의 pixel format을 잡아야 한다"는 1차 판정은 **틀렸다.** 이미 565였고,
범인은 코어가 아니라 **프론트엔드의 캔버스 컨텍스트 속성**이었다.
남은 일은 코어 재빌드가 아니라 **실기에서 이 수정이 같은 폭으로 재현되는지 확인**하는 것이다.
