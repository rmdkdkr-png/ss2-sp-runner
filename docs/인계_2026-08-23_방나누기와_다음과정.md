# 1. 옆방·옆계정 문제 — 정리

## 무엇이 문제였나

방마다 **할 수 있는 일이 다르다.** 이걸 모르면 못 하는 방에서 붙잡고 시간을 버린다.

| | 저장소 읽기 | 저장소 쓰기(푸시) | APK 빌드 |
|---|---|---|---|
| 코드방(구글 열림) | 된다 | **된다** | **된다 — 35초** |
| 원래 방 | 된다 | 안 된다 (403) | 안 된다 |
| 새방 | 된다 | 안 된다 (403) | 안 된다 |

## 왜 그런가 — 깃허브 권한 문제가 아니다

**계정을 협업자로 초대해도 안 고쳐진다.**

푸시가 되는 건 그 **방(세션)이 저장소를 쓰기로 붙였을 때**다. 자격증명이 세션에 붙는 것이지
깃허브 계정 설정으로 되는 게 아니다. 실제로:

- 원래 방 — SANGO 때 **403**
- 새방 — `api.github.com` **403**, `gh` 명령 없음

둘 다 **읽기는 되고 쓰기가 안 된다.**

APK 쪽은 더 분명하다. `dl.google.com` · `maven.google.com` 이 막힌 방은
**안드로이드 SDK·NDK 를 못 받는다.** 깃허브 권한과 아무 상관이 없다.

## 새 방에서 10초 만에 확인하는 법

```sh
# 1) 읽기
git ls-remote https://github.com/rmdkdkr-png/ss2-sp-core >/dev/null && echo 읽기OK

# 2) 쓰기 — 아무것도 안 바꾸면서 인증까지만 해 본다
git -C <클론한자리> push --dry-run origin main && echo 쓰기OK

# 3) APK 빌드 가능 여부
curl -s -o /dev/null -w '%{http_code}\n' https://dl.google.com/android/repository/repository2-3.xml
```

3번이 **200이 아니면 그 방에서 APK 굽지 마라.**

## 그래서 이렇게 나눈다

> **한 방이 쓰고, 나머지는 읽는다.**

- **쓰기·빌드·릴리스** — 구글 열린 방 하나가 전담
- **소스 편집·대사·조사** — 아무 방이나. 결과를 **파일 말고 글로** 넘기면 잃을 일이 없다
- **같은 파일을 두 방에서 동시에 고치지 마라.** `ss2comm.*` 는 코어판·앱판이 공유한다

**옆방이 「APK 를 어느 길로 굽나」 물으면 — 굽지 마라.** 구글 열린 방에서 35초다.
Actions 왕복(10분)을 새로 만들 이유가 없다.

## 컨테이너는 못 믿는다

원래 방 디스크가 **3시간 반 만에 두 번** 8월 21일 시점으로 되돌아갔다.
그때마다 v0.7 이 통째로 날아갔고 사용자가 손수 다시 올려 살렸다.

> **만든 즉시 깃허브에 올린다. 컨테이너 디스크는 임시로만 취급한다.**

`raw.githubusercontent.com` 은 어느 방에서나 읽힌다. 깃허브에 있으면 스스로 되찾는다.

# 3. 다음 과정 — 순서대로

## (1) 대사 생성기 되살리기 ← 지금 여기

### 이게 뭔가

**브라우저판 대사는 「표」가 아니라 「함수」다.** 실행기 안에서 상황을 받아 그때그때 문장을 고른다.
그런데 C 는 자바스크립트를 못 돌리므로, 코어판·앱판은 **미리 뽑아 둔 표**(`ss2comm_lines.h`)를 쓴다.

**생성기는 그 사이를 잇는다** — 함수를 가짜 상황으로 수백 번 돌려 나온 문장을 모으고,
중복을 걷어내고, C 표로 찍는다. 이름 자리에는 `@@NAME@@` 같은 **표식**을 넣고 돌려서
결과의 표식을 `%s` 로 바꾼다. 숫자는 `987654` → `%d`.

### 없으면 뭐가 불편한가

대사 한 줄 고치는 데 **실행기와 헤더 양쪽을 손으로** 고쳐야 한다.
한쪽만 고치면 어긋나고, 나중에 생성기를 돌리는 순간 헤더 쪽 수정이 날아간다.
앞으로 관계 대사 **370줄**을 쓸 텐데 손으로 두 번씩 옮기면 오탈자가 반드시 난다.

### 여기까지 알아냈다

- **실행기가 필요한 것을 이미 밖으로 내보낸다.**
  `window.__ss2` 에 `SPEAKERS` · `SPK_ORDER` · `SPK_KO` 가 실려 있다 (`index.html` 5212줄).
  `SPEAKERS` 는 2541줄, `REPLIES` 는 4121줄, `DUO_PAIR` 는 4104줄.
- **스텁을 쓰지 마라.** 원본 생성기는 `SPEAKERS` 를 떼어내 node 에서 스텁과 함께 돌렸는데,
  인계문이 이미 경고한 함정이 있다 —
  「`pick` 을 "첫 원소 반환" 스텁으로 두면 읽는 쪽이 없는 분기를 상상해 낸다」.
  스텁이 진짜 코드와 어긋나면 **없는 대사가 표에 들어간다.**
- **대신 실행기를 진짜로 띄워서 받아 적어라.** 헤드리스 크로뮴으로 `index.html` 을 열고
  `window.__ss2.SPEAKERS` 를 그대로 부르면 스텁이 필요 없다.
  (구글 열린 방에는 크로뮴이 깔려 있다. `/opt/pw-browsers/`,
  `npm i playwright` 는 `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1` 로)
- **변주 순서를 정렬해서 고정해라.** 원본은 난수 뽑기 순서라 바이트 재현이 불가능했다.
  정렬해 두면 앞으로 diff 가 읽힌다.

### 남은 어려운 곳

**`SPEAKERS` 의 자바스크립트 키(`move`·`moveHit`·`hello`…)와 C 의 `EV_*` 63개를 짝지어야 한다.**
이 대응표가 생성기의 핵심인데 지금 어디에도 안 적혀 있다.

단서는 있다 — 기존 `ss2comm_lines.h` 에 `/* MUSE_M */` 같은 주석이 이벤트 순서대로 박혀 있고,
실행기 함수 이름과 대사 내용을 맞추면 역산된다.

### 검증하는 법

새로 뽑은 표를 기존 `ss2comm_lines.h` 와 대조한다.
**순서는 달라도 되지만 문장 집합은 같아야 한다.** 다르면 대응표나 가짜 입력이 틀린 것이다.

## (2) `commentator_profiles` 를 C 에 넣기

GPT v0.6 JSON 을 C 데이터로 옮긴다. **램을 안 건드리는 작업이라 지금 바로 된다.**

**`false_lore_guards` 부터 걸어라.** 「쥬베이+딸」·「타이잔+화가」 같은 걸
**생성 전 차단 규칙**으로 박아 두면 위 2장의 사고가 구조적으로 막힌다.

## (3) `ANTI_AIR` · `WHIFF_PUNISH` — 값이 이미 다 있다

엔진이 읽는 램은 이렇다 (`ss2comm.c` · `ss2sp.c` 에서 확인):

```
0x0E3E  P1 액션ID (16bit)   ← 필살기는 ≥ 0x180
0x0E3A  P1 Y좌표            ← 지상 = 128. 즉 공중 판별 가능
0x0E54  바라보는 방향
0x1B51  캐릭터 × 2 + 유파    ← 수라/나찰이 여기 들어 있다
0x1DC7  히트스톱             ← 타격이 맞았는지 확인 가능
0x1A46 / 0x1C46  양쪽 체력
0x1B56 / 0x1B57  카드
0x00A7  모드    0x2F82  패드
(P2 는 +0x40 자리에 같은 배치)
```

- **`ANTI_AIR`** = 상대 Y ≠ 128(공중) + 내 공격 액션 + 히트스톱
- **`WHIFF_PUNISH`** = 공격 액션에 들어갔는데 **히트스톱 없이** 끝남(헛침) → 직후 상대 피격

GPT 가 이 둘을 후순위로 뒀는데, **값이 이미 있으니 1순위로 올려도 된다.**

덤: `0x1B51` 에 유파가 있으니 **수라/나찰별로 해설 성격을 바꾸는 것**도 가능하다.

## (4) 점수제 · 침묵 게이트 · 발화 예산

GPT v0.5 규격대로. 지금 엔진은 `emit(ev)` + 쿨다운 구조라,
그 위에 **선택 계층**을 얹는 일이다. 새로 짓는 게 아니다. 789줄 → 1,200줄쯤 될 것이다.

## (5) X 좌표 찾기 → `RANGE_CONTROL`

**Y(`0x0E3A`)는 찾았는데 X 를 아직 안 찾았다.** 바로 옆(`0x0E38` 언저리)일 가능성이 크다.
찾으면 샬롯·소게츠의 핵심 이벤트인 거리 지배가 열린다.

## (6) 추상 이벤트는 마지막

`CHOICE` · `RESTRAINT` · `VALUE_CHANGE` · `ADAPT` · `CLEAN_FUNDAMENTAL`.
램에 「절제」라는 값은 없다. 우리가 규칙을 정해야 한다. **GPT 도 후순위로 뒀고 그 판단이 맞다.**

# 4. 롬에 직접 넣는 것 — 물어봤던 것

**가능은 하나 별개 프로젝트다.**

유리한 점: 이 프로젝트엔 이미 **SS2 한글화 패치(v0.9x)** 가 있다.
즉 **롬에 한글을 넣는 건 이미 해 본 일**이다.

막히는 곳 셋:

1. **엔진을 다시 짜야 한다.** 지금은 밖에서 램을 들여다보는 구조다.
   롬 안에서는 게임 루프에 훅을 걸고 **TLCS-900H 코드**로 돌아야 한다
2. **공간.** 대사 3,700줄 + 글꼴 825자다. 롬 여유가 그만큼 있는지는
   **한글화 패치 만들 때 이미 봤을 것** — 그 방에 물어보면 바로 나온다
3. **띠를 그리는 것.** NGPC 는 타일·스프라이트 기계다. 30픽셀 띠 = 타일 4줄인데
   그 자리를 게임이 쓰고 있다

**현실적인 답**: 대사를 200~300줄로 줄이고 한 줄짜리 짧은 띠면 된다. 지금 규모로는 안 들어간다.

**얻는 것**: 실기에서 돈다. 에뮬레이터도 앱도 필요 없다.
패치 파일(IPS/BPS)만 배포하면 되니 금지선도 안 넘는다.

1. **롬을 어떤 저장소·페이지·아티팩트에도 넣지 않는다.** 세이브스테이트도 마찬가지

3. 꾸러미를 만들 때마다:
   `find . \( -name '*.ngc' -o -name '*.ngp' -o -name 'st_*.bin' \)`
4. **글꼴 파일(BDF)도 저장소에 넣지 않는다.** 임베드는 되지만 재배포는 안 한다.

5. **글꼴에 없는 글자를 대사에 쓰지 마라.** 화면에 공백으로 나온다.
   대사를 먼저 쓰고 `gen_font.js` 를 돌려라
